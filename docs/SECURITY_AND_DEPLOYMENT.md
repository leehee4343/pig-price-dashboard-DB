# 보안 및 배포 원칙

## 현재 대시보드의 역할

`index.html`은 인증 서버가 없는 정적 관리자 분석 화면이다. 브라우저에 전달된 데이터는
사용자가 개발자 도구로 모두 열람할 수 있으므로 이 파일만으로 업체별 접근 권한을 안전하게
구현할 수 없다.

업체가 자기 자료만 조회하는 포털은 다음 구성으로 별도 구현해야 한다.

1. 서버 측 로그인과 세션 관리
2. 사용자 계정과 업체 고유번호의 서버 측 연결
3. 모든 조회 API에서 로그인 업체 조건을 강제로 적용
4. 관리자 역할과 업체 역할의 권한 분리
5. 감사 로그 및 세션 만료

화면에서 업체 선택 상자를 숨기거나 비밀번호를 JavaScript에 넣는 방식은 접근 통제가 아니다.

## 데이터 배포

- 공개 정적 저장소(GitHub Pages)에는 코드만 배포한다. 원본 Excel 파일은 배포 대상이 아니다.
- 실제 데이터는 Supabase(`pig_companies`, `pig_price_records`)에 저장하며, 화면은 매번 이
  DB를 통째로 불러와 브라우저에서 재집계한다(원본 Excel은 업로드 시점에만 브라우저 메모리를
  스쳐 지나간다).
- **업체정보는 원본 Excel의 모든 컬럼을 그대로 저장한다**(팀 확정 방침, 2026-08-25).
  대표자명·주소·연락처·사업자등록번호·담당자 3명의 연락처·업체 API 키(`apikey`)까지 전부
  `pig_companies`에 들어간다.
- Supabase 프로젝트의 anon key는 `public/config/supabase.config.js`에 그대로 노출되어 있고
  Public GitHub 저장소에 커밋되어 있으며, 테이블 RLS도 select/insert/update/delete 전부
  `using (true)`로 열려 있다. 즉 **anon key만 있으면 누구나 위 민감 컬럼을 포함해 DB 전체를
  조회할 수 있다.** 이는 접근 제어 없이 모든 원본 데이터를 저장하기로 한 팀의 명시적 결정에
  따른 결과이며, 실수가 아니다.
- 위 사유로 `pig_companies.apikey`에 들어가는 업체 API 키는 저장되는 시점부터 이미 유출된
  것으로 간주해야 한다. 실제 운영 중인 API 키라면 재발급을 권장한다.
- 사용자가 업로드한 Excel 파일 자체는 브라우저 메모리에서만 파싱되고, 파일 자체는 어디에도
  전송·저장되지 않는다(파싱 결과만 DB에 적재).

과거 Git 이력에 이미 포함됐던 GitHub 토큰과 업체 API 키(이 문서가 작성되기 이전 커밋)는
파일에서 삭제하는 것만으로 폐기되지 않는다. 필요하면 저장소 이력도 정리해야 한다.

## 데이터 갱신

관리자가 사이트 좌측 "데이터 원천 엑셀 업로드"에서 가격정보/업체정보 Excel을 올리면 해당
Supabase 테이블을 전체 삭제 후 새 내용으로 다시 채운다(이력 관리 없음, 매번 현재화).
